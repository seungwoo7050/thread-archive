# 개발 과정: 콘텐츠 검증 테스트 기반

> 프로젝트: 42 Archive Portfolio (`web/portfolio`)
>
> 분류: `07-testing-performance-and-regression-strategy`
>
> 1단계에서 검토·수정한 뒤 고정한 문서 틀을 기준으로 합니다.

## 0. 분류 출처와 변경 가능 범위

- 커밋 SHA·제목·중요도·태그는 해당 브랜치의 `commit/commit-importance.md` 분류와 해당 커밋의 정확한 메타데이터를 기준으로 고정했습니다.
- 이 문서의 개발 과정 목표·커밋 묶음·원본에서 정한 역할은 1단계 분류 검토 결과입니다.
- 2단계에서는 SHA·순서·제목·중요도·태그·역할·질문과 문서 구조를 바꾸지 않습니다.
- 다른 브랜치나 최종 HEAD의 구현을 이전 SHA의 설명으로 소급하지 않습니다.
- 실행 근거는 실제로 수행한 명령만 기록하며, 실행하지 않은 상태를 통과로 해석하지 않습니다.

## 1. 개발 과정 목표

Vitest·jsdom·Testing Library 실행 환경을 만들고, 콘텐츠 입력 처리·공개 선택자·복사 범위·라우트별 데이터 구성 규칙을 차례로 실행 가능한 테스트로 고정하는 과정을 복원합니다.

### 동결된 핵심 불변 조건

- 테스트는 실제 콘텐츠 로더·검증 함수·선택자·뷰 모델을 직접 호출하며, 별도의 모형 구현을 기준 원본으로 삼지 않습니다.
- `getPortfolioContent()`가 반환하는 수정 가능한 집계 객체는 호출마다 분리하며, 읽기 전용으로 취급하는 최상위 메타데이터만 참조를 공유합니다.
- 라우트 뷰 모델은 공용 셸 필드와 라우트 전용 필드만 노출하며 전체 `PortfolioContent` 펼치기를 허용하지 않습니다.
- 알 수 없는 참조를 `null`로 남길지, 제외할지, 다른 값으로 대체할지는 라우트 생성 함수가 결정하며 렌더러는 다시 조회하지 않습니다.

## 2. 이 개발 과정을 이해하기 위한 핵심 질문

- 최초 테스트 기반은 어떤 설정 파일과 준비 코드를 연결했으며, 잘못된 형식의 테스트 입력은 어디에서 주입했는가?
- 공개 모듈의 항목 목록과 복사·참조 범위는 왜 같은 테스트 모음에서 검사하는가?
- 홈, 목록, 상세, 소개, 이력서, 연락처의 선택·순서·대체 처리는 렌더러 이전 어디서 결정되는가?
- 여정과 인터뷰 맵의 해석되지 않은 참조는 각각 어떤 형태로 남거나 제거되는가?

## 3. 완료 기준

- 각 언급된 SHA의 부모 커밋과의 정확한 차이와 변경 후 파일을 확인합니다.
- 커밋별 이전 상태, 구현 결정, 소유 주체와 수명, 실패 경로와 보장하지 않는 범위를 구분합니다.
- 수정은 이전 가정과 근본 원인에 연결하고, 테스트는 실제 코드 경로·검증 방법·증명 범위와 증명하지 않는 범위를 구분합니다.
- 중요도 A는 관련 기능·실패·검증 관계까지, 중요도 B는 해당 커밋의 역할과 후속 연결까지만 설명합니다.
- 개발 과정 전체의 불변 조건 변화, 실패 → 수정 → 테스트의 연결, 소유 주체 이전과 최종 처리 순서를 코드 없이 설명합니다.

# 개발 과정: 라우트 화면의 현재 동작 고정

> 프로젝트: 42 Archive Portfolio (`web/portfolio`)
>
> 분류: `07-testing-performance-and-regression-strategy`
>
> 1단계에서 검토·수정한 뒤 고정한 문서 틀을 기준으로 합니다.

## 0. 분류 출처와 변경 가능 범위

- 커밋 SHA·제목·중요도·태그는 해당 브랜치의 `commit/commit-importance.md` 분류와 해당 커밋의 정확한 메타데이터를 기준으로 고정했습니다.
- 이 문서의 개발 과정 목표·커밋 묶음·원본에서 정한 역할은 1단계 분류 검토 결과입니다.
- 2단계에서는 SHA·순서·제목·중요도·태그·역할·질문과 문서 구조를 바꾸지 않습니다.
- 다른 브랜치나 최종 HEAD의 구현을 이전 SHA의 설명으로 소급하지 않습니다.
- 실행 근거는 실제로 수행한 명령만 기록하며, 실행하지 않은 상태를 통과로 해석하지 않습니다.

## 1. 개발 과정 목표

코드에 고정한 출력 스냅샷 대신 기준 콘텐츠와 쿼리 규칙을 기준으로 App Router 페이지를 현재 동작 고정하고, 다섯 디자인 라우트 출력과 독립 렌더러 구분 지점을 jsdom·브라우저 조합표로 확장하는 과정을 복원합니다.

### 동결된 핵심 불변 조건

- 예상한 문구, 프로젝트와 라우트 활성화 여부는 배포 콘텐츠에서 파생하며 테스트 전용 복제 기준을 만들지 않습니다.
- 누락된·알 수 없는·반복된 `view`·`debug` 쿼리는 라우트 해석 함수의 명시적 대체 처리·첫 번째 값 사용 규칙을 따릅니다.
- 다섯 디자인은 공개 라우트에서 자신을 식별하는 최상위 구분 요소와 주 제목을 유지합니다.
- Design/Classic 독립 렌더러 식별 속성과 공용 디자인 토큰 허용 값 집합은 구조 테스트로 보호됩니다.

## 2. 이 개발 과정을 이해하기 위한 핵심 질문

- jsdom 페이지 테스트가 다섯 디자인 홈과 Classic 라우트 셸에서 무엇을 현재 동작 고정했는가?
- Playwright 조합표가 jsdom이 보지 못하는 응답, 화면 크기, 브라우저 기본 상호작용과 레이아웃 위험을 어떻게 추가했는가?
- 뷰 모델 전환 뒤 다섯 디자인 호환성을 빠르게 확인하는 렌더러 조합표는 어떤 라우트 집합을 사용했는가?
- 렌더러 식별 속성과 CSS 토큰 소스 코드 문자열 검사가 실제 픽셀·동작 보장과 어떻게 다른가?

## 3. 완료 기준

- 각 언급된 SHA의 부모 커밋과의 정확한 차이와 변경 후 파일을 확인합니다.
- 커밋별 이전 상태, 구현 결정, 소유 주체와 수명, 실패 경로와 보장하지 않는 범위를 구분합니다.
- 수정은 이전 가정과 근본 원인에 연결하고, 테스트는 실제 코드 경로·검증 방법·증명 범위와 증명하지 않는 범위를 구분합니다.
- 중요도 A는 관련 기능·실패·검증 관계까지, 중요도 B는 해당 커밋의 역할과 후속 연결까지만 설명합니다.

# 개발 과정: 컴포넌트 상호작용과 하이드레이션 회귀 검증

> 프로젝트: 42 Archive Portfolio (`web/portfolio`)

## 0. 분류 출처와 변경 가능 범위

- 커밋 SHA·제목·중요도·태그는 해당 브랜치의 `commit/commit-importance.md` 분류와 해당 커밋의 정확한 메타데이터를 기준으로 고정했습니다.
- 이 문서의 개발 과정 목표·커밋 묶음·원본에서 정한 역할은 1단계 분류 검토 결과입니다.
- 2단계에서는 SHA·순서·제목·중요도·태그·역할·질문과 문서 구조를 바꾸지 않습니다.
- 다른 브랜치나 최종 HEAD의 구현을 이전 SHA의 설명으로 소급하지 않습니다.
- 실행 근거는 실제로 수행한 명령만 기록하며, 실행하지 않은 상태를 통과로 해석하지 않습니다.

## 1. 개발 과정 목표

브라우저 기본 `<details>` 디자인 선택기의 초기 클라이언트 소유 주체부터 닫기·포커스 상호작용, 하이드레이션 전 경쟁 상태, 결정적인 회귀 테스트와 서버·클라이언트 실행 범위 축소까지 복원합니다.

### 동결된 핵심 불변 조건

- 하이드레이션 전 `details.open`은 브라우저 기본 브라우저 상태이며 React가 초기 서버 예상값으로 덮어쓰지 않습니다.
- 명시적 닫기는 `open`을 제거하고 열기 버튼 요약으로 포커스를 복원합니다.
- 정적 선택자 마크업·콘텐츠·href는 서버 컴포넌트가 소유하고 클라이언트 코드는 명시적 닫기 동작으로 제한됩니다.
- 동작 테스트와 원본 입력 검증 지점 테스트가 각각 상호작용 결과와 소유 주체 설계를 보호합니다.

## 2. 이 개발 과정을 이해하기 위한 핵심 질문

- 초기 선택자가 왜 전체 클라이언트 컴포넌트와 두 DOM 참조를 가졌고 어떤 기능이 아직 없었는가?
- 닫기 버튼과 디자인 링크는 브라우저 기본 `open` 상태와 포커스를 어떻게 바꿨는가?
- 서버 렌더링 뒤 하이드레이션 전 사용자가 펼침 요소를 열면 어떤 불일치가 생기며 어떻게 재현했는가?
- 서버 마크업 전환은 참조·링크 처리기를 어디서 제거하고 어떤 최소 클라이언트 컴포넌트만 남겼는가?

# 개발 과정: 브라우저 접근성 라우트 조합표

> 프로젝트: 42 Archive Portfolio (`web/portfolio`)
>
> 분류: `07-testing-performance-and-regression-strategy`
>
> 1단계에서 검토·수정한 뒤 고정한 문서 틀을 기준으로 합니다.

## 0. 분류 출처와 변경 가능 범위

- 커밋 SHA·제목·중요도·태그는 해당 브랜치의 `commit/commit-importance.md` 분류와 해당 커밋의 정확한 메타데이터를 기준으로 고정했습니다.
- 이 문서의 개발 과정 목표·커밋 묶음·원본에서 정한 역할은 1단계 분류 검토 결과입니다.
- 2단계에서는 SHA·순서·제목·중요도·태그·역할·질문과 문서 구조를 바꾸지 않습니다.
- 다른 브랜치나 최종 HEAD의 구현을 이전 SHA의 설명으로 소급하지 않습니다.
- 실행 근거는 실제로 수행한 명령만 기록하며, 실행하지 않은 상태를 통과로 해석하지 않습니다.

## 1. 개발 과정 목표

브라우저 라우트 테스트 기반 위에서 디자인별 명암 대비, 건너뛰기 링크 포커스 가능 여부, 정의 의미 구조를 수정하고 공용 디자인×활성 라우트 Axe·키보드 조합표로 연결하는 과정을 복원합니다.

### 동결된 핵심 불변 조건

- 각 활성화된 라우트·디자인 출력에는 하나의 main, banner와 `contentinfo` 영역이 존재합니다.
- 건너뛰기 링크는 첫 키보드 포커스가 되고 활성화 뒤 주요 콘텐츠 영역이 프로그래밍 방식의 포커스를 받습니다.
- Foreground 토큰은 표시 영역별 명암 대비 요구에 맞게 분리되며 정의 목록은 term·값 의미 구조를 유지합니다.
- Accessibility 테스트 모음과 일반 E2E 테스트 모음은 동일한 활성 라우트·디자인 조합표를 사용합니다.

## 2. 이 개발 과정을 이해하기 위한 핵심 질문

- 초기 Playwright 라우트 조합표가 접근성 자동화의 어떤 브라우저·서버 기반을 제공했는가?
- 밝은·어두운 표시 영역에 하나의 색상 토큰을 재사용한 가정은 어떻게 수정되었는가?
- 해시 대상 `main`에 `tabIndex={-1}`가 필요한 이유와 누락된 Brutalist 보강 순서는 무엇인가?
- Axe 태그, 주요 영역 개수와 건너뛰기 링크 키보드 테스트가 무엇을 증명하고 무엇을 놓치는가?

## 3. 완료 기준

- 각 언급된 SHA의 부모 커밋과의 정확한 차이와 변경 후 파일을 확인합니다.
- 커밋별 이전 상태, 구현 결정, 소유 주체와 수명, 실패 경로와 보장하지 않는 범위를 구분합니다.
- 수정은 이전 가정과 근본 원인에 연결하고, 테스트는 실제 코드 경로·검증 방법·증명 범위와 증명하지 않는 범위를 구분합니다.
- 중요도 A는 관련 기능·실패·검증 관계까지, 중요도 B는 해당 커밋의 역할과 후속 연결까지만 설명합니다.
- 개발 과정 전체의 불변 조건 변화, 실패 → 수정 → 테스트의 연결, 소유 주체 이전과 최종 처리 순서를 코드 없이 설명합니다.

## 0. 분류 출처와 변경 가능 범위

- 커밋 SHA·제목·중요도·태그는 해당 브랜치의 `commit/commit-importance.md` 분류와 해당 커밋의 정확한 메타데이터를 기준으로 고정했습니다.

## 1. 개발 과정 목표

클라이언트 등장 효과 상태, 전역 글꼴 로딩과 자동 라우트 사전 로딩를 줄이고 실제 브라우저 요청·글꼴 동작 및 브라우저 기본 상호작용 지연 시간를 회귀 테스트로 고정하는 과정을 복원합니다.

### 동결된 핵심 불변 조건

- 코어 콘텐츠 표시 여부는 하이드레이션·IntersectionObserver progress에 의존하지 않습니다.
- 글꼴 미리 로딩·소비자는 언어·렌더러 필요 범위로 제한되고 Geist Mono는 검토한 초기 라우트에서 불필요하게 요청되지 않습니다.
- 내부 링크는 유휴 상태·화면 표시 기반 라우트 사전 로딩를 명시적으로 끄되 사용자가 시작한 탐색은 유지합니다.
- 디자인 선택기 닫기와 모바일 메뉴 열기는 정의된 Event Timing 측정에서 표본 3개의 중앙값과 최댓값이 200ms 이하를 목표로 합니다.

## 2. 이 개발 과정을 이해하기 위한 핵심 질문

- 등장 효과의 관찰자·상태 실행 주기를 제거하면 어떤 애니메이션을 포기하고 어떤 서버 렌더링 우선 불변 조건을 얻는가?

# 개발 과정: 시각 회귀와 반응형 기준선

## 0. 분류 출처와 변경 가능 범위

- 커밋 SHA·제목·중요도·태그는 해당 브랜치의 `commit/commit-importance.md` 분류와 해당 커밋의 정확한 메타데이터를 기준으로 고정했습니다.
- 이 문서의 개발 과정 목표·커밋 묶음·원본에서 정한 역할은 1단계 분류 검토 결과입니다.
- 2단계에서는 SHA·순서·제목·중요도·태그·역할·질문과 문서 구조를 바꾸지 않습니다.
- 다른 브랜치나 최종 HEAD의 구현을 이전 SHA의 설명으로 소급하지 않습니다.
- 실행 근거는 실제로 수행한 명령만 기록하며, 실행하지 않은 상태를 통과로 해석하지 않습니다.

## 1. 개발 과정 목표

Playwright 라우트·화면 크기 기반과 렌더러·토큰 구조 규칙 위에 다섯 디자인 반응형 화면 캡처 기준선과 정확한 스냅샷 목록을 추가하는 과정을 복원합니다.

### 동결된 핵심 불변 조건

- 시각 기준선은 배포 라우트·디자인 출력과 설정된 데스크톱·모바일 프로젝트에서 생성됩니다.
- 화면 캡처 전 동작 줄이기 설정, 네트워크 idle, 글꼴 배포 준비 상태와 이미지 안정화를 기다립니다.
- 홈은 다섯 디자인 데스크톱·모바일, 첫 번째 프로젝트 상세는 다섯 디자인 데스크톱 기준선을 정확히 갖습니다.
