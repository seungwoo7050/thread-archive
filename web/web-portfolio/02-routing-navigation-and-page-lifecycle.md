- 내부 최상위 경로 기준 URL만 변환하며 절대 URL과 프로토콜 상대 URL은 그대로 둡니다.

### 1. `902eddcef875` — feat(navigation): 템플릿 URL과 쿼리 해석 추가

#### 해당 커밋에서 확인할 내용

- 부모 `7c95a6f387b4`와 비교해 `src/lib/portfolio/selectors.ts` 및 새 `src/lib/portfolio/template-href.ts`의 책임이 어디서 시작되는지 확인합니다.

- `createTemplateHref`가 기존 쿼리와 해시를 분해하고 `URLSearchParams`로 `view`와 `debug`를 갱신한 뒤 재조립하는 순서를 적습니다.

#### 복원 결과

**이전 상태와 문제**

부모 `7c95a6f387b4`에는 콘텐츠 집계 객체 로더와 선택자가 있었지만, 라우트 쿼리를 해석하거나 내부 URL에 선택한 디자인·디버그 상태를 다시 싣는 공통 규칙은 없었습니다. 따라서 각 호출자가 문자열을 직접 조립하면 기본 디자인 처리, 기존 쿼리와 해시 보존, 외부 URL 비변형 규칙이 서로 달라질 위험이 있었습니다.

**구현 결정과 실행 경로**

- `src/lib/portfolio/selectors.ts`
  - `resolveHomeTemplateId(value, presentation)`은 배열이면 첫 항목만 선택합니다.
  - 선택값이 `presentation.templates`에 실제로 존재할 때만 그 ID를 반환하고, 그 외에는 `presentation.defaultHomeTemplate`로 돌아갑니다.
  - `resolveContentDebug(value)`도 배열의 첫 값을 사용하며 정확히 `"content"`일 때만 `true`입니다.
  - `getTemplateHref(...)`는 콘텐츠 파일에 정의된 기본값 ID를 채워 `createTemplateHref(...)`에 위임합니다.
- `src/lib/portfolio/template-href.ts`
  - 템플릿 ID가 없거나 href가 `/`로 시작하지 않거나 `//`로 시작하면 원문을 즉시 반환합니다.
  - 해시를 먼저 떼고, 남은 값을 경로·쿼리로 분리한 뒤 `URLSearchParams`를 만듭니다.
  - 비기본 디자인 또는 `alwaysInclude`이면 `view`를 설정하고, 기본 디자인이면 기존 `view`를 삭제합니다.
  - `contentDebug`가 true일 때만 `debug=content`를 설정합니다.
  - 마지막에 경로, 쿼리, 해시를 원래 순서로 다시 결합합니다.

핵심 코드는 다음 규칙입니다. 이 발췌는 이 커밋의 `src/lib/portfolio/template-href.ts`에서 확인한 내용입니다.

```ts
if (!templateId || !href.startsWith("/") || href.startsWith("//")) {
  return href;
}

if (options.alwaysInclude || templateId !== defaultTemplateId) {
  params.set("view", templateId);
} else {
  params.delete("view");
}
```

**소유권과 실패 처리 지점**

URL 변환 중 생성되는 `URLSearchParams`는 함수 호출 내부의 일시 객체이며 브라우저 방문 기록이나 전역 상태를 소유하지 않습니다. 잘못된 디자인 값은 예외가 아니라 설정된 기본값으로 정규화됩니다. 반면 잘못된 형식의 URL 전체를 일반 URL 파서로 검증하지는 않습니다. 이 도우미 함수는 애플리케이션 내부에서 `/`로 시작하는 href를 입력으로 받습니다.

**보장**

- 내부 URL의 기존 쿼리와 해시를 보존하면서 `view`/`debug`만 규칙적으로 갱신합니다.
- 남아 있는 기본값 `view`를 제거할 수 있습니다.
- 외부 절대 URL과 프로토콜 상대 URL은 손대지 않습니다.
- 반복된 쿼리의 라우트 해석은 첫 값에 고정됩니다.

**비보장과 후속 관계**

이 SHA에는 해당 도우미 함수를 실행하는 테스트가 없습니다. 따라서 이 절의 결과는 정확한 변경 내용과 함수 코드 정적 검토로 확정한 것이며 실행 결과가 아닙니다. 홈 라우트 소비는 `f4233f024890`, URL 구분 지점 회귀는 `3353032ba23b`, 기본값 소유 주체 명시는 `b669e04c0932`에서 이어집니다.

- back/forward 탐색에서 상태가 복원되는지

**보장과 비보장**

동일한 현재 설정에서는 기존 URL 결과를 유지하면서 의존성을 드러냅니다. 테스트 입력들은 새 필수 속성을 제공하도록 수정되었습니다. 그러나 변경 내용에서 별도의 “기본값을 다른 ID로 바꾼 경우” 전용 단언문이 새로 추가된 것은 확인되지 않았습니다. 따라서 대체 기본값 동작은 `createTemplateHref` 구현과 명시적인 전달으로 정적 검토했으며 새 실행 시점 회귀 결과로 과장하지 않습니다.

- 최상위 경로 기준 내부 href는 기존 쿼리와 해시를 유지하면서 디자인·디버그 상태를 정규화합니다.
- 알 수 없는 디자인은 설정된 기본값으로 복귀합니다.
- 기본 디자인은 필요하지 않으면 URL에서 제거되고, 선택기처럼 명시가 필요한 호출자는 `alwaysInclude`를 사용할 수 있습니다.
- 외부 및 프로토콜 상대 URL은 변형하지 않습니다.
- 실행 시점 실행 증거는 기록하지 않았습니다. 정확한 커밋 코드와 테스트 원본을 정적 검토했습니다.

5. 도우미 함수는 내부 URL만 쿼리와 해시 보존 방식으로 다시 만들고 `Link` 또는 기준 소비자에 돌려줍니다.

- main: `id="main-content"`와 `data-home-template={homeTemplate}` — 건너뛰기 대상이자 페이지 콘텐츠 주요 영역
- 건너뛰기 링크: `href="#main-content"`

이 구조는 시각 디자인 범위와 의미상 main 영역을 같은 요소에 강제로 결합하지 않습니다.

**소유 주체**

`PageShell`이 셸 문구, 디자인 범위, 주요 영역, 헤더·푸터 조립을 소유합니다. 각 라우트는 현재 선택된 템플릿·디버그·현재 경로를 준비해 넘깁니다. `DesignSwitcher` 내부의 펼침 요소·포커스·하이드레이션 문제는 여기서 해결되지 않으며 다음 개발 과정의 책임입니다.

이 커밋에는 이 구조를 새로 실행 검증하는 테스트가 포함되지 않았습니다. 정확한 변경 내용으로 조립과 속성 순서를 확인했습니다.

`suppressHydrationWarning`과 회귀 테스트로 경쟁 상태를 다룰 수 있었지만, 선택자의 대부분은 정적 링크 마크업입니다. 전체 컴포넌트를 클라이언트 실행 범위로 유지하면 브라우저 기본 펼침 요소를 쓰면서도 모든 목록 마크업과 참조를 hydrate해야 합니다. 근본 원인를 더 좁히면 클라이언트 JavaScript가 필요한 동작은 명시적 닫기 후 포커스 복원뿐입니다.

**구조 변경**

- `DesignSwitcher`에서 최상위 `"use client"`, `useRef`, 참조 attachment를 제거합니다.
- 디자인 목록, 요약, `<details>` 요소, 링크는 서버에서 렌더링한 마크업이 됩니다.
- 새 `src/components/portfolio/design-switcher-close.tsx`만 클라이언트 컴포넌트입니다.
- 닫기 버튼은 클릭 이벤트의 현재 대상에서 `closest("details")`를 찾고, 직접 하위 요약 요소를 `:scope > summary`로 찾습니다.
- `<details>` 요소의 `open`을 제거한 뒤 요약이 있으면 포커스합니다.
- 디자인 링크의 `onClick` 닫기 처리기는 제거됩니다. 실제 탐색이 펼침 요소의 현재 페이지 수명을 끝냅니다.
- 브라우저가 관리하는 상태 차이를 허용하는 `suppressHydrationWarning`은 `<details>` 요소에 남습니다.

**소유 주체 이동**

| 이전 | 이후 |
| --- | --- |
| 선택기 전체 마크업과 참조가 클라이언트 | 정적 선택자 마크업은 서버 |
| DOM 참조가 컴포넌트 수명에 고정 | 닫기 버튼이 클릭 시 로컬 DOM ancestry를 찾음 |
| 링크 클릭도 명령형 닫기 | 탐색에 페이지 전환 효과 책임 |
| 명시적 닫기·포커스와 정적 목록이 같은 구분 지점 | 명시적 닫기만 작은 최소 클라이언트 컴포넌트 |

기존 테스트도 구조에 맞게 바뀝니다. 링크 클릭 닫기 단언문은 제거되고, href 생성과 명시적 닫기·포커스 계약은 유지됩니다.

이 리팩터링은 동작을 확장하기보다 하이드레이션 대상과 클라이언트 소유 주체를 최소화합니다. `DesignSwitcherClose`가 없는 입력에만 의존하는 서버 컴포넌트로 만들 수 없는 이유는 명시적 닫기 버튼이 현재 DOM을 닫고 요약에 포커스를 돌리는 명령형 동작 때문입니다.

| 초기 auxiliary 라우트 | 소개, 이력서, 연락처가 검사 단계 없이 생성됨 |
| 선택자 도입 | 누락된·true는 활성화된, false만 비활성화된 |
| new 선택적 라우트 | 여정과 인터뷰 맵이 도입 시부터 검사 단계 사용 |
| 라우트 공통 수정 | 기존 소개·연락처·프로젝트·이력서도 콘텐츠 로딩 직후 검사 단계 적용 |

최종 불변 조건은 “선택적 페이지 설정값이 명시적인 false이면 해당 지원 여부의 모든 소유한 라우트가 페이지별 work 전에 `notFound()`로 종료한다”입니다.

## 7. 실패 → 수정 → 테스트 관계

수정과 테스트를 실제로 바로잡거나 검증한 이전 가정 및 구현에 연결합니다.

- **이전 가정:** 탐색·설정이 라우트 접근 가능성도 자연스럽게 통제할 것이라는 암묵적 상태.
- **실제 위험:** 기존 라우트는 선택자가 생긴 뒤에도 호출자가 아니어서 직접 URL 접근이 계속 가능.
- **최상위 cause:** 페이지 사용 가능 여부가 데이터 모델에만 있고 라우트 구분 지점 강제 적용가 일관되지 않음.
- **수정:** `50199...`가 초기 라우트와 프로젝트 deep 링크 모두에 같은 검사 단계를 추가.
- **회귀 근거:** 이 선택한 개발 과정에는 전용 테스트 커밋이 없습니다. 후속 라우트 조합표가 존재하더라도 실행하거나 이 커밋의 직접 회귀로 소급하지 않았습니다.

호출자와 호출 대상의 담당 범위, 브라우저·프레임워크 상태, 자원 수명, 이 개발 과정에서 의도적으로 제외한 범위를 추적합니다.

3. 매개변수 await
4. 해석 함수로 원본 projectId 기반 `currentPath`와 쿼리 맥락 준비
5. `getProjectById`
6. 누락된이면 `notFound()`
7. 성공하면 준비된 `shellProps`로 렌더링

알 수 없는 프로젝트에서도 맥락 객체는 한 번 계산되지만 셸은 조회 성공 후에만 렌더링됩니다. 프로젝트 조회를 도우미 함수에 넣지 않은 덕분에 공통 맥락이 데이터 영역별 실패를 소유하지 않습니다.

- 2단계 완료: 검토 후 고정한 문서 틀을 바탕으로 개발 과정 문서 일곱 개를 완성했습니다. `README.md`까지 포함하면 파일은 여덟 개입니다.
- 저장소 근거: 모든 고정 커밋을 해당 SHA에서 GitHub 연결 도구로 정적 검토했으며, 제목과 변경 내용을 브랜치의 `commit/commit-importance.md`와 대조했습니다.
- 조상 관계 검증: SHA 33개가 모두 해당 브랜치의 선형 분류에 있습니다. GitHub 비교에서도 각 기준 SHA가 `web/portfolio`와의 병합 기준점으로 확인됐고 `behind_by: 0`는 0이었습니다. `902eddcef875` 뒤에는 464개, `b669e04c0932` 뒤에는 29개 커밋이 있습니다.
- 저장소 테스트 실행: 수행하지 않았습니다. 로컬 실행 환경에서 원본 체크아웃을 만들 수 없었습니다.
- 실행한 환경 확인:
  - 명령: `git ls-remote --heads https://github.com/seungwoo7050/42-archive.git web/portfolio`
  - 결과: 종료 상태 `128`; `Could not resolve host: github.com`
- 따라서 변경 이력의 코드·테스트 정적 검토와 실제 실행 결과를 구분했습니다. Vitest, Playwright, Next 빌드, 서버 명령은 실행했다고 기록하지 않았습니다.
