# 실행 환경 조립과 리버스 프록시의 변화

- 카테고리: `09-production-delivery-and-release-engineering` — 제품 전달과 릴리스 엔지니어링
- 저장소: `https://github.com/seungwoo7050/42-archive`
- 브랜치: `web/ft_transcendence`

## 1. 학습 목표

PostgreSQL, Fastify API, Next.js 웹, Caddy를 하나의 실행 단위로 조립한 초기 Compose에서 시작해, 개발용 소스를 마운트한 실행 환경과 외부 게이트웨이가 운영 배포 구조로 발전하는 과정을 복원합니다.

이 문서는 완성된 해설이 아니라 정확한 SHA를 순서대로 확인해 제품 전달 구조의 발전을 복원하기 위한 작업 틀입니다.

### 직접 관련된 불변 조건

- 브라우저가 접근하는 외부 진입점은 Caddy의 단일 오리진이며 API, WebSocket, 웹 UI의 전달 경로가 구분됩니다.
- API는 DB 사용 가능 상태 이후에 시작하고 웹은 API와 함께 재현 가능한 여러 서비스로 구성된 실행 환경으로 조립됩니다.
- 운영 실행 명령을 선택한 실행 환경은 웹 빌드 결과를 실제 운영 서버로 실행해야 합니다.
- 외부에 공개하면 안 되는 내부 운영 엔드포인트는 게이트웨이에서 명시적으로 차단됩니다.
- 초기 소스를 마운트한 Compose와 최종 변경 불가능한 이미지 기반 실행 환경의 차이를 구분할 수 있어야 합니다.

## 2. 핵심 질문

- 초기 `docker-compose.yml`은 어떤 서비스, 포트, 볼륨, 의존성을 소유합니까?
- Caddy의 `/api/*`, `/ws`, 기본값 처리 함수가 외부 URL을 내부 서비스로 어떻게 전달합니까?
- API와 웹이 개발 명령에서 운영 실행 명령 경로로 이동하면서 빌드와 실행 순서가 어떻게 달라집니까?
- Caddy 설정이 바인드 마운트에서 이미지에 포함된 산출물로 바뀌는 이유는 무엇입니까?
- `/api/metrics` 같은 내부 엔드포인트가 외부 게이트웨이에서 차단되는 실제 라우팅 규칙을 확인할 수 있습니까?

- 최종 전달 소유 주체: 루트 `build` 스크립트가 워크스페이스 생성 측 순서를, 각 패키지가 자신의 산출물을, `verify:build`와 CI가 선택한 출력 계약을 소유합니다.
- 소스와 운영 산출물의 관계: 개발 조건부 내보내기는 소스를 유지하지만 운영용 내보내기/시작은 `dist`와 `.next/standalone`을 소비합니다.
- 빌드 시점과 실행 설정의 관계: Next 독립 실행과 공개 설정은 빌드 단계에서 만들어지고 API/DB는 컴파일된 JS를 실행할 때 소비합니다. 이 개발 흐름은 실행 시점 비밀값 주입을 다루지 않습니다.
- 시작·준비 상태·종료 계약: 이 개발 흐름은 산출물 생성 측과 소비 측만 정의하며 프로세스 준비 상태와 종료는 후속 개발 흐름의 책임입니다.
- 차단 조건: 루트 빌드의 선행 단계 실패와 빌드 후 누락된 경로가 셸/CI를 0이 아닌 종료 상태로 종료합니다.
- 검증 가능한 것과 외부 배포 환경에 남는 것: 정확한 SHA 변경 내용으로 내보내기, 빌드 스크립트, 검사기 경로와 CI 호출을 확인했습니다. 실제 pnpm 빌드나 산출물 검사기를 실행하지 않았으므로 실행 근거는 기록하지 않습니다.

## 1. 학습 목표

이 문서는 완성된 해설이 아니라 정확한 SHA를 순서대로 확인해 제품 전달 구조의 발전을 복원하기 위한 작업 틀입니다.

### 직접 관련된 불변 조건

- 운영 API와 웹 컨테이너는 시작 시 의존성 설치나 소스 빌드를 수행하지 않습니다.
- 실행 이미지에는 실행에 필요한 산출물과 의존성만 포함되며 애플리케이션 프로세스는 루트 권한이 아닌으로 실행됩니다.
- DB 마이그레이션은 API와 분리된 일회성 서비스가 완료된 뒤 API가 시작됩니다.
- DB/API/웹 내부 포트는 필요한 서비스 사이에만 노출되고 외부 공개 지점은 게이트웨이로 제한됩니다.

- 애플리케이션 경기방 작업 종료 허용 시간보다 컨테이너 종료 유예 시간이 짧아서는 안 됩니다.

- 최종 전달 소유 주체: 각 Dockerfile이 불변 API·웹 산출물을, Compose가 DB·마이그레이션·준비 상태·게이트웨이·프로세스 종료 수명주기를, 정적 계약 테스트가 선택한 설정 불변 조건을 소유합니다.
- 소스와 운영 산출물의 관계: 실행 시점 컨테이너에는 소스 바인드 마운트나 시작 빌드가 없고 빌드 단계가 만든 컴파일된/독립 실행 산출물만 실행기에 복사됩니다.
- 빌드 시점과 실행 설정의 관계: 웹 `NEXT_PUBLIC_*`는 이미지 빌드 시점, DB URL과 세션 비밀값은 컨테이너 실행 시점입니다. 필수 비밀값은 Compose 변수 치환에서 먼저 검사됩니다.
- 시작/준비 상태/종료 계약: DB 정상 → 마이그레이션 성공 → API 정상 → 웹 정상 → Caddy 공개이며, API 종료 유예 시간은 70초로 60초 경기방 작업 종료보다 깁니다.
- 차단 조건: 비밀값 누락, DB 비정상, 마이그레이션 실패, API나 웹이 비정상이면 하위 소비 패키지 공개를 막습니다. 종료 유예 시간 60초 미만은 계약 테스트를 실패시킵니다.
- 검증 가능한 것과 외부 배포 환경에 남는 것: 정확한 SHA Dockerfile/Compose/테스트 소스와 변경 내용을 검사했습니다. Docker 데몬을 사용한 이미지 빌드, Compose 시작, 신호/종료 준비 명령은 실행하지 않았습니다.

## 10. 최종 빌드·전달 순서

```text
build context (`.dockerignore`)
→ dependencies stage (frozen workspace install)
→ builder (shared → DB/API 또는 shared → Next)
→ non-root API/Web runner images
Compose interpolation: required secrets
→ PostgreSQL healthy
→ one-shot compiled migration exit 0
→ API healthcheck healthy
→ Web healthcheck healthy
→ Caddy image가 :8080만 publish
stop: SIGTERM → application drain ≤ 60s → expected process exit before 70s grace
```

위 흐름을 각 단계의 실제 파일, 명령, 산출물, 프로세스와 연결해 다시 작성합니다.

## 1. 학습 목표

### 직접 관련된 불변 조건

- 운영 배포 검증은 소스 개발 서버가 아니라 빌드된 산출물/프로세스를 실행해야 합니다.

- 실제 PostgreSQL을 준비하고 마이그레이션한 뒤 API 준비 상태를 확인한 후 실행 확인/브라우저 검증을 진행합니다.
- 비회원/체험 브라우저 작업도 운영 스타일 빌드/시작 경로를 사용하되 PostgreSQL 없이 제한된 권한을 검증합니다.
- 쿠키 오리진은 HTTP 세션 동작 의미와 일치해야 하며 CI의 호스트명 차이도 계약으로 취급합니다.
- 처리 과정 자체의 필수 작업/명령/실행 시점 규칙은 정적 계약 테스트로 보호됩니다.

- 시작/준비 상태/종료 계약: PostgreSQL 상태 확인과 마이그레이션 뒤 API/웹 프로세스를 시작하고 주기적 조회 성공 후 실행 확인/브라우저를 실행하며 종료 처리가 PID를 정리합니다.
- 차단 조건: 설치/빌드/마이그레이션/준비 상태/실행 확인/E2E/정적 검증 중 하나라도 실패하면 작업이 0이 아닌 종료 상태입니다. 정확한 localhost 출처도 정적 검사입니다.
- 검증 가능한 것과 외부 배포 환경에 남는 것: 저장소의 정확한 SHA에서 워크플로와 테스트 코드를 검사했습니다. 이 세션에서 GitHub Actions·pnpm·PostgreSQL·Playwright를 재실행하지 않았으므로 새 실행 결과는 주장하지 않습니다.

## 10. 최종 빌드·전달 순서

```text
push/PR
→ pinned Node/pnpm + frozen install
→ typecheck/unit/static contracts/build + artifact verification
├─ PostgreSQL integration job
├─ process/browser job:
│  PostgreSQL health → package migration → compiled API + production Web
│  → readiness → HTTP smoke → WS smoke → authenticated Playwright
└─ guest browser job:
   demo build → compiled API + production Web → readiness → guest-only Playwright
all background processes → shell trap/hosted-runner teardown
workflow source → `tests/ci-contract.test.mjs` exact contract assertions
```

위 흐름을 각 단계의 실제 파일, 명령, 산출물, 프로세스와 연결해 다시 작성합니다.

# 실행 환경 버전과 의존성 보안 계약

- 카테고리: `09-production-delivery-and-release-engineering` — 제품 전달과 릴리스 엔지니어링

## 1. 학습 목표

Node/pnpm 도구 버전 집합을 로컬 메타데이터, 패키지 실행 엔진, CI, Docker 이미지와 계약 테스트 사이에서 하나의 릴리스 계약으로 고정하고, Node·Next.js·WebSocket·운영 의존성 보안 패치가 매니페스트와 잠금/강제 버전 지정 의존성 그래프에 일관되게 반영되는 과정을 복원합니다.

이 문서는 완성된 해설이 아니라 정확한 SHA를 순서대로 확인해 제품 전달 구조의 발전을 복원하기 위한 작업 틀입니다.

### 직접 관련된 불변 조건

- 로컬 버전 파일, 패키지 관리자, 패키지 실행 엔진, CI, Docker 이미지가 같은 정확한 실행 시점 버전 계약을 사용합니다.
- 실행 시점 버전 기대값은 여러 계약 테스트에 문자열로 복제하지 않고 표준 `.node-version`에서 읽습니다.
- CI 설치는 정확한 pnpm과 동결된 잠금 파일을 사용해 매니페스트와 확정된 의존성 그래프의 편차를 차단합니다.
- 직접 의존성 보안 패치는 해당 워크스페이스 매니페스트와 `pnpm-lock.yaml` 해석을 함께 갱신합니다.
- 취약한 간접 의존성은 루트 `pnpm.overrides`와 잠금 파일 의존성 그래프에서 최소 수정된 버전으로 강제할 수 있습니다.
- 버전 변경 커밋은 의존성/실행 의존성 그래프를 바꾸지만 취약점 순회 통과나 애플리케이션 실행 시점 성공 자체를 검증하지 않습니다.

## 2. 핵심 질문

- Node/pnpm 범위를 처음 고정한 파일과 이후 정확한 실행 엔진 pin이 추가로 필요했던 이유는 무엇입니까?
- `.node-version`을 표준 소스로 읽는 계약 테스트가 어떤 중복된 버전 문자열의 편차를 제거합니까?

# 운영 설정 오류와 영속 저장소 누락의 즉시 차단

- 브랜치: `web/ft_transcendence`

## 1. 학습 목표

운영 설정 픽스처를 먼저 영속 PostgreSQL 전제에 맞춘 뒤, 명시적 `APP_MODE=production`과 `NODE_ENV=production` 모두에서 `DATABASE_URL`이 없으면 API 시작 전에 거부하고, 체험 모드의 의도된 메모리 저장소만 허용하는 릴리스 경계를 복원합니다.

이 문서는 완성된 해설이 아니라 정확한 SHA를 순서대로 확인해 제품 전달 구조의 발전을 복원하기 위한 작업 틀입니다.

### 직접 관련된 불변 조건

- 명시적인 `APP_MODE=production`과 `NODE_ENV=production`에서 추론된 운영은 모두 영속 데이터베이스 URL을 요구합니다.
- 운영은 `DATABASE_URL` 부재를 메모리 저장소 선택으로 조용히 대체하지 않습니다.
- DB 요구 조건은 애플리케이션/저장소 생성 이전 설정 파싱 단계에서 실패 시 차단합니다.
- 체험 모드는 PostgreSQL 없이 메모리 저장소를 사용할 수 있는 별도의 제한된 신뢰/권한 모드입니다.
- 설정 단위 테스트는 모드 판단과 실패를 검증하지만 PostgreSQL 접근 가능 여부, 마이그레이션, 트랜잭션 영속성은 검증하지 않습니다.

| 회귀 테스트 근거 | `apps/api/src/env.test.ts` | 단위 테스트/CI | 테스트 프로세스 수명 | 세 가지 사례 조합표 불일치 시 테스트 실패; 외부 DB 근거 없음 |

## 9. 최종 상태

- 최종 전달 소유 주체: 실행 환경 파서가 운영 모드와 영속 DB 요구 조건의 실패 시 차단 경계를, 저장소 구성이 파서 성공 후 백엔드 수명을, 단위 테스트가 모드 조합표 회귀를 소유합니다.
- 소스와 운영 산출물의 관계: 컴파일된 API 산출물도 시작에서 동일 환경 설정 파서를 실행하므로 소스/빌드 형식과 무관하게 운영 DB 요구 조건이 적용됩니다.
- 빌드 시점과 실행 설정의 관계: `DATABASE_URL`, `APP_MODE`, `NODE_ENV`는 API 실행 설정이며 웹 빌드 시점 공개 모드와 별도입니다.
- 시작/준비 상태/종료 계약: 설정 파싱이 가장 앞선 검사입니다. 통과 후에만 DB 풀/저장소/서버 시작과 준비 상태가 진행됩니다. 종료 동작은 이 개발 흐름 범위가 아닙니다.
- 차단 조건: 명시적 또는 추론된 운영에서 DB URL이 없으면 시작 전에 거부합니다. 체험 누락된 DB는 의도된 허용 조건입니다.
- 검증 가능한 것과 외부 배포 환경에 남는 것: 정확한 SHA 파서/테스트 변경 내용으로 판단 조합표를 확인했습니다. 단위 명령, PostgreSQL 연결, 마이그레이션, 프로세스 시작은 이 세션에서 실행하지 않았습니다.

## 10. 최종 빌드·전달 순서

```text
process environment
→ basic schema parse
→ application mode resolve
   ├─ `APP_MODE=production`
   └─ `APP_MODE` absent + `NODE_ENV=production`
→ production? `DATABASE_URL` required
   ├─ missing → configuration error → no repository/server acquisition
   └─ present → parsed config → PostgreSQL repository/startup path
`APP_MODE=demo` + no DB
→ parsed demo config → intentional memory repository path
unit matrix protects explicit production / inferred production / demo
```

위 흐름을 각 단계의 실제 파일, 명령, 산출물, 프로세스와 연결해 다시 작성합니다.
