# 워크스페이스·패키지·애플리케이션 구성 경계

- 카테고리: `01-foundations-and-api-boundaries` — 애플리케이션 기반과 API 경계
- 저장소: `https://github.com/seungwoo7050/42-archive`
- 브랜치: `web/ft_transcendence`

## 1. 학습 목표

단일 저장소를 공유 패키지, 데이터베이스 패키지, API 애플리케이션, 웹 애플리케이션으로 나누고, 시작 코드가 각 의존 객체의 생성·초기화·종료 순서를 조립하는 과정을 복원합니다.

이 문서는 1단계 카테고리 감사 후 동결된 작업 틀을 기준으로, 정확한 SHA 순서에 따라 구현이 발전한 과정을 복원합니다.

### 직접 관련된 불변 조건

- 워크스페이스 의존성은 루트 → 패키지 명령 위임과 `shared`/DB → API와 웹의 단방향 소비로 구성됩니다.
- 공유 패키지는 전송 표현을 소유하지만 영속 저장소 드라이버와 브라우저/실행 시 구현을 포함하지 않습니다.
- PostgreSQL 풀과 Kysely 클라이언트는 저장소 구현이 보유하고, 구성 진입점은 백엔드 선택과 초기화·종료 호출 순서를 관리합니다.
- 웹 애플리케이션은 공유 TypeScript 소스를 트랜스파일하지만 DB 구현은 브라우저 번들에 포함하지 않습니다.

## 2. 핵심 질문

- 실제 개발 이력에서 컴파일 시점 DTO와 게임 계약이 DB/API/웹 패키지보다 먼저 도입된 이유는 무엇입니까?
- DB 패키지가 의존성만 선언한 초기 상태에서, 외부에서 마이그레이션을 실행할 수 있고 저장소 수명주기를 관리하는 형태로 발전한 단계는 무엇입니까?
- `apps/api/src/index.ts`가 생성하는 객체와 각 객체가 내부적으로 소유하는 자원을 구분할 수 있습니까?
- 초기화 코드는 정상 종료 시 무엇을 보장하며, 시작 중 초기화가 실패했을 때 무엇을 아직 정리하지 못합니까?

## 3. 완료 기준

- 커밋 목록의 모든 SHA가 지정 브랜치의 커밋 이력에 포함되는지 확인합니다.
- 각 SHA를 부모 커밋 또는 직전 관련 SHA와 비교해 변경 전후 상태를 구분합니다.
- 파일, 심벌, 호출자와 피호출자, 상태 변경, 실패 분기, 정리 과정을 해당 시점의 실제 코드로 기록합니다.
- 수정 커밋은 이전 가정과 근본 원인을 연결하고, 테스트 커밋은 실제 코드 경로와 검증 범위·미검증 범위를 구분합니다.
- S/A/B/C 중요도에 따라 설명의 깊이를 구분합니다.
- 실행하지 않은 명령의 결과는 작성하지 않으며, 코드 검토와 실행 증거를 구분합니다.
- 마지막 SHA까지만 사용해 개발 흐름의 최종 소유 주체, 불변 조건, 실행 순서를 정리합니다.

4. 검증된 ID/본문을 저장소 메서드에 전달합니다.
5. 저장소 결과를 엔드포인트 응답 스키마로 파싱합니다.
6. 성공이면 타입이 지정된 JSON을 반환합니다.
7. 예상 실패는 `ApiHttpError`, 예상 밖 실패는 일반 내부 오류 응답 구조로 변환됩니다.

# 엄격한 JSON 요청 검증

- 카테고리: `01-foundations-and-api-boundaries` — 애플리케이션 기반과 API 경계
- 저장소: `https://github.com/seungwoo7050/42-archive`
- 브랜치: `web/ft_transcendence`

## 1. 학습 목표

본문이 없는 라우트의 국소 정규화 문제에서 출발해 모든 JSON 라우트의 경로 매개변수/쿼리/본문을 엄격한 공유 계약으로 정의하고 업무 로직 전에 공통 파서로 집행한 뒤 전체 라우트 회귀 테스트로 고정하는 과정을 복원합니다.

이 문서는 1단계 카테고리 감사 후 동결된 작업 틀을 기준으로, 정확한 SHA 순서에 따라 구현이 발전한 과정을 복원합니다.

### 직접 관련된 불변 조건

- 모든 현재 JSON 라우트는 untrusted 경로 매개변수/쿼리/본문을 업무 로직 전에 엄격한 스키마로 검증합니다.
- 본문이 없는 라우트도 명시적 빈 객체 계약을 가져 알 수 없는 쿼리/본문을 허용하지 않습니다.
- 검증 실패는 저장소 변경 전에 공통 형식이 정해진 오류 응답 형식으로 종료됩니다.
- 전달된 클라이언트 주소는 명시적으로 프록시를 신뢰하지 않는 한 신원이나 요청 빈도 제한 키를 바꾸지 못합니다.

## 2. 핵심 질문

- `request.body ?? {}`라는 로컬 수정이 왜 전체 라우트 계약 목록으로 일반화되어야 했습니까?
- 빈 경로 매개변수/쿼리/본문 계약이 본문이 없는 GET/POST의 정의되지 않은 필드를 어떻게 거부합니까?
- `parseHttpRequest`가 반환한 값만 저장소 호출에 쓰인다는 근거는 무엇입니까?
- 라우트 조합표 테스트가 검증하는 검증 범위와 새 라우트 추가 시 남는 수동 책임은 무엇입니까?

# WebSocket 클라이언트 오류 경계와 내부 오류 격리

## 1. 학습 목표

WebSocket 메시지 파싱 실패와 명령/저장소 처리 실패가 한 오류 처리에 결합되어 있던 상태를 분리하고, 내부 예외 원문을 고정된 외부 공개 메시지로 비밀값 제거한 뒤 결정적 저장소 실패 주입으로 검증하는 과정을 복원합니다.

이 문서는 1단계 카테고리 감사 후 동결된 작업 틀을 기준으로, 정확한 SHA 순서에 따라 구현이 발전한 과정을 복원합니다.

### 직접 관련된 불변 조건

- 잘못된 클라이언트 메시지 본문은 `invalid_event`, 서버 측 처리 실패는 `internal_error`로 구분됩니다.
- 저장소·SQL·내부 호스트·원래 예외 메시지는 클라이언트에 노출되는 WebSocket 이벤트에 포함되지 않습니다.
- 파싱 실패는 명령 전달 전에 즉시 반환하고 처리 실패는 동일 연결의 공개 오류 이벤트로 격리됩니다.

## 2. 핵심 질문

- 파싱 단계와 비동기 처리 저장소 명령 단계를 분리하면 공개 코드와 실패 소유 주체가 어떻게 달라집니까?

초기 로컬 실행 환경 기본값과 브라우저 CORS 설정에서 출발해 개발/테스트/운영/체험 모드, 강한 비밀값, 명시적 프록시 신뢰, 잘못된 모드 실패 시 차단, 운영 영속 저장소 요구 조건을 하나의 검증된 환경 파서로 수렴시키는 과정을 복원합니다.

이 문서는 1단계 카테고리 감사 후 동결된 작업 틀을 기준으로, 정확한 SHA 순서에 따라 구현이 발전한 과정을 복원합니다.

### 직접 관련된 불변 조건

- 환경별 권한은 `readAppMode`가 반환한 검증된 단일 모드에서 파생됩니다.
- 명시적 모드 오타는 개발로 하향 전환되지 않고 시작 오류가 됩니다.
- 운영은 강한 세션 비밀값과 `DATABASE_URL` 없이는 환경 파싱을 통과하지 못합니다.
- 체험은 의도적으로 메모리 저장소를 허용하며 프록시 주소 파싱은 `TRUST_PROXY=1`일 때만 활성화됩니다.
- credentialed 브라우저 변경에 필요한 출처, 메서드, 헤더는 CORS 설정에 명시됩니다.

- 운영과 체험의 영속 저장 권한이 어떤 조건에서 갈라집니까?
- CORS 메서드/헤더, `credentials: true`, 프록시 신뢰는 각각 다른 신뢰 결정을 어떻게 표현합니까?

| `readEnv`/`readAppMode` | 환경 값 파싱, 모드/비밀값/저장소/신뢰 검증 | DB 연결 준비 상태를 소유하지 않습니다. |
| Fastify CORS 플러그인 | 출처/메서드/헤더/credentialed CORS 사전 요청 응답 | CSRF·쿠키 브라우저 강제 검사를 소유하지 않습니다. |
| 애플리케이션 구성 진입점 | 검증된 환경 설정으로 저장소/애플리케이션 옵션 선택 | 모드 문자열 해석을 중복하지 않습니다. |
| 설정 테스트 | 순수 실행 환경 픽스처와 보호 조건 결과 | 실제 프로세스/브라우저/DB를 실행하지 않습니다. |

## 9. 최종 상태

- 최종 SHA 기준으로 모드는 한 파서에서 결정되고 명시적 오타는 거부됩니다.
- 체험/운영은 강한 비밀값을 요구하며 운영만 영속 DB URL을 반드시 요구합니다.
- 프록시 신뢰는 명시적으로 활성화해야 하고 브라우저 변경용 CORS 메서드/헤더가 선언됩니다.
- 실제 DB 연결·마이그레이션 준비 상태·브라우저 CORS 사전 요청 실행은 이 개발 흐름의 코드 검토와 단위 테스트만으로 검증되지 않습니다.

### 실행 검증 기록

- 원문 검토: GitHub 연결 도구로 커밋 목록의 정확한 SHA 변경 내용과 필요한 과거 파일을 조회했습니다.
- 브랜치 검증: 브랜치 내부 `commit/commit-importance.md`가 선언한 433개 선형 이력에서 모든 참조 SHA와 원문 분류를 대조했고, 가장 이른 참조 `b625c4f9dfdc`는 브랜치 최종 상태 비교에서 병합 기준 커밋이 동일 SHA임을 확인했습니다.
- 실제 실행 시도: `git clone --branch web/ft_transcendence --single-branch https://github.com/seungwoo7050/42-archive.git /tmp/ft-transcendence-audit`
- 결과: 종료 상태 128, `Could not resolve host: github.com`. 따라서 저장소 체크아웃, 패키지 설치, 테스트 명령은 실행하지 않았으며 실행 시점 결과를 주장하지 않습니다.

## 10. 최종 실행 흐름

1. 실행 환경 객체에서 명시적 APP_MODE를 우선 검사합니다.
2. 없으면 NODE_ENV 운영/테스트를 해석하고 그 외는 개발을 사용합니다.
3. 체험/운영이면 세션 비밀값 바이트 길이를 검사합니다.
4. 운영이면 DATABASE_URL 존재를 검사합니다.
5. TRUST_PROXY가 정확히 `1`인지 읽어 환경 설정 객체를 반환합니다.
6. 구성 진입점이 검증된 모드/DB/신뢰 값을 저장소와 Fastify 옵션에 전달합니다.
7. 브라우저 요청은 설정된 CORS 출처/메서드/헤더 규칙을 통과한 뒤 라우트에 도달합니다.
