# 개발 스레드 01: 실행 가능한 프로토콜·HTTP 계약 검증

영문 제목: **Executable Protocol and HTTP Contract Verification**

## 개발 스레드 목표

공유 스키마가 실제 API와 실시간 신뢰 경계에서 실패 시 차단으로 적용되고, 구형·알 수 없는·불완전 입력이 비즈니스 로직에 도달하지 않는 과정을 복원합니다.

## 핵심 질문

- 컴파일 시점 TypeScript 타입과 실행 중 파서의 보장 범위는 어떻게 다릅니까?
- 엄격한 스키마를 정의하는 것과 모든 라우트가 그 스키마를 실제 호출하는 것은 왜 별도 단계입니까?
- 버전, 순번, 저장 결과 구분 필드가 어떤 잘못된 상태 조합을 막습니까?
- 표 기반 라우트 회귀는 적용 누락을 어떤 방식으로 탐지하며 무엇을 자동으로 포괄하지 못합니까?

## 완료 기준

- WebSocket·HTTP 스키마 단위 테스트와 실제 라우트 통합 테스트의 역할을 구분합니다.
- 각 SHA에서 허용·거부되는 구체적인 형식을 해당 시점 코드로 설명합니다.
- 계약 정의 → 적용 → 전체 라우트 회귀 테스트의 순서를 재구성합니다.
- 정의되지 않은 필드, 잘못된 경로, 버전이 없는 이벤트, 불완전한 영속 저장 메타데이터의 실패 위치를 설명합니다.

테스트는 `reset → db-latency → db-down → db-up → edge-latency → edge-reset → edge-up → reset` 명령 순서와 두 번의 250ms 대기를 정확히 비교합니다. 보고서는 시작/종료 시각, 대상, 설정, 정렬된 단계, 지연 시간 실행 시간, DB 중단 본문, 소켓 초기화 오류를 보존해야 합니다.

별도 실패 사례에서 `db-down` 명령이 예외를 던져도 마지막 초기화가 호출되는지 확인합니다. 또한 루프백이 아닌 URL은 실행기가 어떤 명령도 수행하기 전에 거부됩니다.

- 중간 제어 실패에서도 정리 초기화가 보장됩니다.

#### 이 커밋이 보장하지 않는 것

- 실제 Toxiproxy·PostgreSQL·경계 프로세스가 예상 상태로 변하는지는 이 단위 테스트가 검증하지 않습니다.
