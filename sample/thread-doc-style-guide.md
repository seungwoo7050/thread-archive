# Dev Thread 문서 작성 규칙

> 적용 대상: 42 프로젝트(ft_printf, libft, small-shell, philo, minishell, ft_irc, miniRT,
> inception, ft_transcendence 등)의 개발 흐름을 커밋 단위로 복원하는 모든 Thread 문서.
> 기존 문서를 재작성할 때도, git repo + Thread 정의 자료를 보고 신규로 쓸 때도 이 규칙을
> 그대로 적용한다 — 둘은 최종 산출물 스펙이 동일하고 입력 소스(정의 자료의 출처)만 다르다.

## 0. 이 규칙이 지키려는 것

이 문서 세트의 목적은 "학습 기록"이 아니라 **재사용 가능한 개발 답지**다. 미래의 독자가 이
Thread의 커밋을 몰라도, 문서만으로 "무엇을 왜 그렇게 만들었는지"를 그대로 재구성할 수 있어야
한다. 이 기준에서 벗어나는 모든 섹션 — 정보량 없이 형식만 채우는 반복, 학습자용 체크리스트,
근거 없는 확신 — 은 전부 제거 대상이다.

핵심 3원칙:
1. **같은 사실은 최대 2번까지만** — "이 사실이 생긴 지점"에서 한 번 상세히, 필요하면
   "최종 요약 지점"에서 한 번. 3번째 반복이 나오면 그 문서는 리팩터링 대상이다.
2. **섹션은 필요할 때만 만든다.** 템플릿에 슬롯이 있다고 다 채우지 않는다. 커밋 성격이
   다르면 섹션도 달라야 한다 — 이게 이 규칙의 가장 중요한 원칙이다.
3. **모르는 건 모른다고 쓴다.** diff만으로 확정할 수 없는 부분은 추측해서 확신 있게 쓰지
   않는다.

## 1. 문서 전체 구조

```
# Thread: <불변 조건/책임을 설명하는 제목>
> Project: `<project>` · 문서 번호: <NN> (또는 branch 등 식별 메타데이터)

## 개요
  (서사 + 커밋 목록 표 + [선택] 최종 상태 표)

## <커밋 섹션> × N
  (아키타입별로 구조가 다름 — 3장 참고)
  (커밋이 5개 이상이고 자연스러운 하위 클러스터가 있으면 그룹 헤더로 묶는다)

## 이 Thread의 경계
  (다루지 않는 인접 관심사 + 알려진 경우 담당 sibling Thread 지목)

> 검토 범위: <실제로 확인한 것과 확인하지 않은 것>
```

제목은 구현 디테일이 아니라 **이 Thread가 확립하는 불변 조건이나 책임**을 설명해야 한다.
나쁜 예: `Thread: memcpy와 memmove 커밋들`. 좋은 예: `Thread: 비중첩 복사와 겹침 안전 이동의
책임 분리`.

## 2. 개요 작성 규칙

- **서사 우선**: 커밋을 그냥 나열하지 말고, 이 커밋들이 왜 이런 순서로 얽혀 있는지 1~2
  문단으로 설명한다. 정상 경로 구현/실패 주입 계측/실제 복구 로직/검증처럼 **역할군으로
  묶어서** 서술하면 좋다. Thread 안의 커밋 순서가 SHA 시간순과 다를 수 있다는 걸 전제로 쓴다
  — "이 개발단위는 나노입자처럼 섞여 있다"는 게 이 문서 시리즈의 원래 문제의식이다.
- **최종 상태 표는 선택**: Thread가 여러 개의 구분되는 종료 경로/결과를 갖는 경우
  (예: 정상 완주 / 각 실패 지점 / 각 결과 코드)에만 표로 요약한다. 결과가 단일하면
  (예: "함수 하나가 이런 계약을 만족한다") 굳이 넣지 않는다.
- **커밋 목록 표는 항상 포함**: `순서 | SHA | 제목 | 중요도 | 태그 | 역할`. 제목/중요도/태그는
  Thread 정의 자료(구버전 문서 또는 commit-importance.md)에서 **그대로 가져온다** — 여기서
  재해석하거나 다시 매기지 않는다. 역할은 한 문장으로 압축.
- **개요는 예고만 한다**: 각 커밋의 상세 내용(문제/원인/diff)은 본문 섹션에 맡긴다. 개요에서
  이미 다 설명해버리면 본문과 중복된다. 예외적으로 Thread 전체를 관통하는 한계나 트레이드오프
  (예: "실패 주입이 A 경로는 덮지만 B 경로는 안 덮는다")는 개요에서 존재만 언급하고, 상세
  설명은 그 사실이 실제로 드러나는 커밋 섹션에 둔다.

## 3. 커밋 섹션 — 아키타입별 구조

**커밋 성격이 섹션 구조를 결정한다.** 아래는 관찰된 8개 아키타입과 각각의 권장 구조다. 이
목록은 완전하지 않다 — 새로운 성격의 커밋을 만나면 새 구조를 만들어도 된다. 판별 신호는
커밋 메시지의 conventional-commit prefix, diff 크기/모양, Thread 내 위치를 함께 본다.

| 아키타입 | 판별 신호 | 권장 섹션 순서 |
| --- | --- | --- |
| 핵심 feat (자원/위험이 처음 생김) | Thread의 첫 유의미한 구현 | 무엇을 만들었는가(diff/코드) → 설계 결정 근거 → 아직 다루지 않는 것 → [선택]흐름도 → 관련 커밋 |
| 트리비얼/셋업 feat (아직 이 Thread의 핵심 위험이 없음) | 자원이 하나뿐, 겹침/실패 등 아직 발생 안 함 | 무엇을 만들었는가(간략) → **"왜 가볍게 다루는가"** → [선택]눈여겨볼 설계 → 관련 커밋 |
| 중간 빌드업 feat (능력이 아직 불완전) | 다음 커밋에서 확장될 게 diff에서 보임 | 무엇이 바뀌었는가(diff) → **"무엇을 준비하는가, 아직 없는 것"** → 관련 커밋 |
| enabling refactor (seam만 추가, 동작 무변화) | 제목이 `refactor`, 실제로는 테스트 가능성만 열어줌 | **장르 선언 한 문장**("이 커밋은 앞뒤의 feat/fix와 성격이 다르다") → **"왜 필요한가"** → diff → production no-op 보장 명시 → 관련 커밋 |
| fix (일반) | 제목이 `fix`, 실제 동작 변경 | **"왜 바뀌었는가 (문제→원인→결정)"** → diff 또는 주석-최종코드(4장 기준) → [선택]실패/성공 흐름도 → "보장하는 것/보장하지 않는 것" → 관련 커밋 |
| 아주 작은 fix (1~3줄) | diff가 한 hunk, 몇 줄 | diff → **"왜 이렇게 작은가"**(크기 정당화, 필요시 중요도가 낮게 매겨진 이유를 헤지 표현으로 추측) → 관련 커밋 |
| test — 일반 회귀 | 이전 fix를 고정하는 표준 케이스 | "무엇을 검증하는가" → 관련 diff 스니펫 → "증명하는 것/증명하지 않는 것" → 관련 커밋 |
| test — 새 기법 도입 | 이전 테스트와 관찰 방식 자체가 다름(예: 종료코드 대신 leak 직접 관찰) | **"왜 다른 기법이 필요한가"**(이전 테스트의 한계) → 기법 설명+diff → "증명하는 것/증명하지 않는 것" → 관련 커밋 |

**공통 헤더 포맷**: 모든 커밋 섹션은 `## <SHA> — <커밋 제목>` 뒤에
`**중요도** \`X\` · **태그** \`A, B, C\`` 한 줄로 시작한다.

**관련 커밋** 섹션은 항상 "왜 관련되는가"를 한 절로 붙인다. bare `다음은 X다` 금지 —
"X가 이 seam을 실제로 사용한다", "X가 이 가정을 깬다" 처럼 관계의 성격을 명시한다.

## 4. diff vs 주석-최종코드 선택 기준

- **기본값은 diff**다 — 100% 신규 추가(`+`만 있는 diff)라도 diff 형식으로 보여준다. 이게
  "이 커밋이 파일 안에서 정확히 뭘 바꿨는지"를 가장 정직하게 보여주는 형태다.
- **줄 단위 설명이 실제로 가치를 더할 만큼 로직이 조밀할 때만** diff 대신 주석 달린 최종
  코드 블록(plain \`\`\`c, `-`/`+` 없이 `//` 주석)으로 전환한다 — 예: 상태 전이가 여러
  단계인 retry 카운터, short-circuit을 이용한 트릭, 여러 실패 모드를 한 반환값에 압축하는
  함수. 이 경우 **같은 커밋이 다른 곳(호출부 등)도 바꿨다면, 그 변경은 별도로 diff 블록으로
  이어서 보여준다** — "새 로직 자체"는 주석-코드로, "기존 코드의 표면적 수정"은 diff로 분리.
- **이 Thread와 무관한 hunk는 diff에서 아예 제외**한다. 한 커밋이 여러 관심사를 섞어
  담고 있으면(예: string precision fix + 무관한 zero-padding 추가) 이 Thread 주제와
  관련된 hunk만 인용한다. 생략 사실이 독자를 헷갈리게 할 수 있으면("이 작은 커밋에 왜 이것만
  있지?") 한 줄로 짧게 언급하고, 명백히 boilerplate 생략이면 언급하지 않아도 된다.
- **`/* ... */` 같은 elision 표시**는 diff 안에서 흥미롭지 않은 부분(예: envp 구성 로직)을
  건너뛰는 데 써도 된다 — 단, 이 Thread의 불변 조건과 관련된 부분을 가려서는 안 된다.

## 5. 정직성 규칙

- **`> [확인 필요]`**: diff와 그 시점 source만으로 특정 주장을 확정할 수 없을 때 이 마커로
  명시한다. 무엇이 불확실한지, 무엇을 봐야 확정할 수 있는지까지 써준다. 절대 추측을 사실처럼
  쓰지 않는다.
- **헤지 표현 필수**: 커밋 메시지/diff에 명시되지 않은 의도나 이유를 추론할 때는
  "~로 보인다", "~로 추정된다" 류의 표현을 반드시 쓴다. (예: 중요도가 왜 `S`가 아니라
  `B`로 매겨졌는지 추측하는 경우.)
- **중요도/태그는 절대 재해석하지 않는다.** Thread 정의 자료(구버전 문서 또는
  commit-importance.md)에 있는 값을 그대로 옮긴다. 자료에 값이 없는 커밋을 다뤄야 한다면
  임의로 등급을 매기지 말고 `[확인 필요]`로 남긴다.
- **`검토 범위:` 줄은 항상 마지막에 넣는다.** 정확히 어떤 SHA의 diff/source를 확인했는지,
  무엇을 실행하지 않았는지(테스트 바이너리, sanitizer 등)를 명시한다.

## 6. 언어와 포맷

- 본문은 한국어. SHA, 함수/변수/파일명, 태그 값(`FORMAT`, `CORE`, `RISK` 등), C 키워드는
  영어 그대로 유지한다 — 한국 개발자 커뮤니티에서 자연스러운 관례를 따른다.
- 섹션 헤더는 완결된 서술형 문장/질문으로 쓴다 ("무엇이 바뀌었는가 (diff)", "왜 이렇게
  작은가"). 체크리스트형 명사구 나열 금지.
- **금지 패턴**:
  - `학습자 기록 —`, `원자료 기준`, `자가 점검` 같은 메타 라벨/프리픽스
  - 커밋마다 반복되는 "핵심 질문", "완료 기준" 같은 self-check 섹션
  - 불변조건 ledger, 소유권 변화 표처럼 커밋 섹션 내용을 다른 각도로 또 요약하는 상위 표
    (개요의 "최종 상태" 표 하나로 충분하다)
  - Thread 마무리를 "다음 Thread"라는 순서 개념으로 서술하는 것 — Thread는 병렬로 존재할
    수 있으므로 8장의 "주제 경계" 방식만 쓴다

---

## 7. 그룹 헤더

커밋이 5개 이상이고, 그 안에서 자연스러운 하위 주제가 나뉜다면(예: "단일 allocation
공통 규칙" 3개 + "list lifecycle" 2개 + "검증" 1개) `##` 커밋 헤더보다 상위인 소제목으로
묶는다. 커밋이 3개 이하로 적은 Thread에서는 그룹 헤더를 만들지 않는다 — 나눌 만큼의 양이
안 된다.

---

## 8. Thread의 경계 (닫는 섹션)

- 이 Thread가 다루지 않는 인접 관심사를 나열한다.
- **Thread 정의 자료를 통해 그 관심사를 담당하는 다른 Thread를 알고 있다면, 그 문서/Thread를
  실제로 지목한다** (`01-parsed-representation-to-conditional-execution의 몫이다` 처럼).
  다른 Thread 문서가 아직 안 쓰여 있어도, Thread 정의 자료에 있는 이름/번호로 지목할 수
  있으면 지목한다.
- 모르면 "별개의 문제다" 정도로 존재만 언급한다 — 순서 관계(“다음 Thread”)를 임의로
  만들어내지 않는다. 병렬 구조를 전제로, **"이 문서가 다루지 않는 범위"** 로만 서술한다.

## 9. 최종 QC 체크리스트 (Thread 단위, 1회만 확인)

작성 후 아래를 확인한다. 이건 문서 안에 넣는 섹션이 아니라 작성자(또는 에이전트)의 마지막
자체 검수용이다.

- [ ] 같은 사실이 3번 이상 반복되는 곳이 없다
- [ ] 모든 커밋 섹션이 그 커밋의 실제 성격에 맞는 구조를 쓰고 있다 (3장 표를 기계적으로
      다 채우지 않았다)
- [ ] 중요도/태그가 Thread 정의 자료와 정확히 일치한다 (재해석 없음)
- [ ] 추론된 주장에는 헤지 표현이 붙어 있다
- [ ] 확정 불가능한 지점은 `[확인 필요]`로 남아 있고, 지어낸 확신이 없다
- [ ] "이 Thread의 경계" 섹션이 순서("다음 Thread")가 아니라 주제 경계로 서술되어 있다
- [ ] 마지막에 `검토 범위:` 줄이 있다
- [ ] 금지 패턴(6장) 중 어느 것도 남아 있지 않다
